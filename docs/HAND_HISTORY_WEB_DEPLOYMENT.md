# SICFUN Hand-History Web Deployment

This guide is for the packaged Windows hand-history review product under `dist/hand-history-web`.

**See also:** [`docs/OPERATOR_RUNBOOK.md`](OPERATOR_RUNBOOK.md) (particularly section 5A) for the day-to-day operator-on-the-host workflow: source-tree launchers, service install / start / drain-stop / uninstall scripts, log triage entries (the Troubleshooting section walks three web-specific triage flows -- the upload-UI-404-with-health-200 case for `STATIC_DIR` misconfig, the `/api/ready` `503` + `/api/health` `200` flow for the three `readyReason` triggers, and the OIDC silent-failure case where users report Google sign-in fails but no `auth.oidc.failure` log entries appear), and deeper observability + security notes that this guide summarizes but the runbook owns. The two docs are complementary -- this one is the packaged-release reference (and ships verbatim as the bundle root's `README.md` so customers reach it without needing the source tree), the runbook is the day-to-day operations companion.

## Two Release Variants

Two release scripts produce two artifact shapes. Both serve the same web app; the difference is what they bundle for the host.

| Script | Output | Java handling | Click-to-run |
|---|---|---|---|
| `scripts/release-hand-history-web.ps1` | `dist/hand-history-web/` directory only | Requires Java 17+ on `PATH` | No |
| `scripts/release-hand-history-web-installer.ps1` | Same directory **plus** versioned outer ZIP at `dist/hand-history-web-<version>.zip` | Embeds a jlink runtime under `runtime/bin/java.exe`; falls back to PATH if missing | Yes: `Setup.cmd` verifies the manifest then launches the service |

Use the installer variant when the target host may not have Java pre-installed.

## What You Ship

The release bundle contains:

- `bin/run-hand-history-web.ps1`: start the app directly
- `bin/install-hand-history-web-service.ps1`: install an NSSM-backed Windows service
- `bin/start-hand-history-web-service.ps1`: start the service and wait for readiness
- `bin/drain-stop-hand-history-web-service.ps1`: drain and stop the service cleanly
- `bin/uninstall-hand-history-web-service.ps1`: remove the service
- `bin/verify-release-manifest.ps1`: verify bundle integrity against `manifest.sha256`
- `conf/hand-history-web.env`: runtime configuration template
- `static/`: packaged upload UI
- `lib/`: application jars
- `model/`: optional packaged model artifacts if they were included at build time

Installer-variant additions:

- `Setup.cmd`: click-to-run entry point that verifies the manifest then launches the service
- `runtime/`: jlink-trimmed Java runtime; the launcher and service-common shim prefer this over `PATH`
- `runtime/BUILD_INFO.txt`: source JDK version and jdeps-detected module list

## Host Prerequisites

- Windows host
- PowerShell 5.1+
- Java 17+ on `PATH` before startup (not required for the installer variant — `runtime/` is embedded)
- NSSM if you want the Windows service workflow (drop `nssm.exe` into `bin/` before zipping or pass `-NssmPath` at install time; auto-download is disabled because corporate AV often blocks `nssm.cc`)
- Client browser: a modern build (Chrome 103+, Edge 103+, Firefox 100+, Safari 16+) gets the one-line `AbortSignal.timeout` fetch-timeout path. Older browsers fall back to an `AbortController + setTimeout` shim that delivers the same fetch-timeout safety net; that primitive shipped in Chrome 66 / Firefox 57 / Safari 11.1 (2018+) which is below the page's actual rendering floor, so every browser that can run the page also gets the timeout. `String.prototype.replaceAll` (used by HTML escaping) requires Chrome 85+ / Edge 85+ / Firefox 77+ / Safari 13.1+ — that's the real floor below which the page won't render at all. Modern Edge is Chromium-based so it tracks the Chrome version.

## Quick Start

From the package root:

```powershell
powershell -ExecutionPolicy Bypass -File .\bin\verify-release-manifest.ps1
powershell -ExecutionPolicy Bypass -File .\bin\run-hand-history-web.ps1
```

Default behavior:

- Binds to `127.0.0.1:8080`
- Serves the upload UI from `static/`
- Loads settings from `conf/hand-history-web.env` (override the file location via `-ConfigFile <path>` on the launcher CLI or `CONFIG_FILE=<path>` in the environment — useful when one host runs multiple sicfun instances on different ports with sibling config files)
- Exposes `/api/health` for liveness and `/api/ready` for readiness
- Exposes async job endpoints for hand-history analysis and Playing Hall simulation (see "HTTP Endpoints" below)

## HTTP Endpoints

`/api/health` and `/api/ready` are unauthenticated and accept `GET`, `HEAD`, and `OPTIONS`. HEAD returns the same status code and security headers as the corresponding GET but with no body, which has two distinct status-code stories worth keeping straight when wiring up a monitor: a `/api/ready` HEAD probe returns `200` while idle and `503` when readiness fails (queue full / draining / timed-out worker) -- the same status a GET probe would see -- so a HEAD-vs-GET monitor switch on `/api/ready` saves only the JSON body's bandwidth; a `/api/health` HEAD probe ALWAYS returns `200` because the endpoint itself has no `503` path (it's a pure liveness probe; see the always-200 invariant + `ok: true` body field in "Logs And Observability" below). The practical upshot: wire load balancers and readiness checks against `/api/ready` (so a `503` actually means "stop sending traffic"), and wire pure is-the-process-up monitors against `/api/health` (so the only failure mode is transport-layer -- TCP refused / DNS / HTTP error -- and a `200` is unconditional confirmation the JVM accepted and answered the request). The hand-history analysis and Playing Hall job routes enforce whichever auth mode is configured (Basic auth or platform-user); on a no-auth deployment (loopback default, or non-loopback with `ALLOW_UNAUTHENTICATED_PUBLIC_BIND=true`) they accept anonymous requests. Either way they are rate-limited (Submit / JobStatus buckets — see "Rate limiting" below); rate limiting runs independently of auth. Auth bootstrap routes under `/api/auth/*` are open by design (login/register cannot require an existing session). Submissions return `202 Accepted` with `Location` and `Retry-After` headers plus a JSON body containing `jobId`, `status` (always the literal string `"queued"` on a fresh `202` — the worker hasn't started yet; the GET poll endpoint surfaces later state transitions), `statusUrl`, `submittedAtEpochMs`, `pollAfterMs`.

The read-only endpoints `/api/auth/me`, `/api/analyze-hand-history/jobs/{jobId}`, and `/api/playing-hall/jobs/{jobId}` also accept `HEAD` alongside `GET`. The HEAD response carries the same status code, security headers, response-control headers (`Allow`, `Retry-After` on 503), AND content-variant headers (`Content-Encoding: gzip` whenever a GET with the same `Accept-Encoding` would compress -- the body length must clear the 256-byte MinGzipSize floor where gzip header overhead would otherwise cost more than it saves; `Vary: Accept-Encoding` always for compressible response types) as the corresponding GET response but with no body, so a probe that only needs to check existence or rate-limit posture can skip the JSON payload -- AND a cache that validates via HEAD before refetching via GET sees identical variant headers across both hops, avoiding the spurious invalidation a HEAD-vs-GET Content-Encoding mismatch would trigger (the failure mode is operator-invisible apart from inflated egress: the cache silently discards its stored entry on every refresh and re-fetches the full body, which never logs as an error). Static asset routes share the same HEAD/GET variant-header symmetry and additionally emit `ETag` / `Last-Modified` so HEAD-driven `304` revalidation works the same way GET-driven would (a HEAD with `If-None-Match: <weak-tag>` returns `304` instead of `200` on a cache hit, saving the body bytes on the validation hop).

All body-reading endpoints (`POST /api/auth/*`, `POST /api/analyze-hand-history`, `POST /api/playing-hall`) require `Content-Type: application/json` and return `415 Unsupported Media Type` otherwise. The `application/json; charset=utf-8` form is also accepted. The check forecloses a cross-origin form-CSRF vector against the login endpoint (a hostile site auto-submitting an HTML `<form action="/api/auth/login">` would send `application/x-www-form-urlencoded` and now bounces at the Content-Type guard before any parsing). The same endpoints also reject `Content-Encoding` values other than absent or `identity` with 415; the server does not decompress request bodies, so accepting `Content-Encoding: gzip` would either produce a confusing "invalid JSON" 400 or, worse, open a zip-bomb vector against `MAX_UPLOAD_BYTES`.

Error responses across the JSON API (400 invalid input, 401 unauthorized, 403 CSRF / forbidden, 404 unknown / not-yours, 405 method not allowed -- emits an `Allow` response header listing the supported methods per RFC 7231 sec 6.5.5, 409 has two distinct triggers: `"playing hall job already terminal"` from `DELETE /api/playing-hall/jobs/{id}` when the job already reached completed/failed/cancelled state, AND `"already signed in"` from `POST /api/auth/register` / `POST /api/auth/login` when the request carries a valid session cookie (the frontend treats this 409 as a state-divergence signal and refreshes `/api/auth/me` to flip the UI to the signed-in state -- typically fires when the user has the auth form open in two tabs and signed in via the other one), 413 oversize, 415 wrong Content-Type/Encoding, 429 rate-limited, 500 internal server error -- emitted on an unhandled handler exception, the JSON body just reads `"internal server error"` so the JVM stack trace stays in the audit log instead of the client response, 503 draining / queue full / timed-out-worker still unwinding -- all three fire from the same admission gate, with the JSON body's `error` text naming the specific trigger (`... service is draining; try another instance or retry later` / `... queue is full; try again later` / `... worker timed out; instance is waiting for recovery`) and a `Retry-After: 5` header set by default when a handler doesn't supply a more specific value) all return `Content-Type: application/json; charset=utf-8` with a body of `{"error": "<message>"}`. 429 responses additionally include three sibling fields: `retryAfterSeconds` (integer; mirrors the `Retry-After` header so a client without header access can still get the value from the body), `rateLimitBucket` (one of `submit` / `job-status` / `auth` — the bucket that fired; useful for client-side per-bucket backoff state), and `limitPerMinute` (integer; the configured cap the request hit — lets a script tell "the bucket is just at its default" from "the operator tightened the cap recently"). 4xx/5xx bodies are stable enough for scripted clients to display `body.error` verbatim, with the caveat that the messages are operator-readable English rather than i18n-keyed.

Hand-history analysis:

- `POST /api/analyze-hand-history` — submit a hand history for analysis. Body: JSON `{handHistoryText, heroName?, site?}`. `handHistoryText` is required (whitespace-only and BOM-only payloads are rejected with `400`); `heroName` is capped at 64 chars and may not contain C0 control characters or DEL (defense in depth against log injection if any future code path logs the value); `site` accepts one of the recognised aliases (`pokerstars`/`stars`/`winamax`/`wina`/`ggpoker`/`gg`/`ggnetwork`), or the literal string `auto` / an absent/empty value to ask the server to auto-detect from the file's first non-empty line, and is otherwise capped at 64 chars before any other validation runs. Rate-limited as Submit.
- `GET /api/analyze-hand-history/jobs/{jobId}` — poll job status. Returns `200` with `status=queued` / `running` / `completed` / `failed`, the universal fields `jobId` / `statusUrl` / `submittedAtEpochMs` / `startedAtEpochMs` / `completedAtEpochMs` (the latter two are `null` until the worker reaches each transition), and `pollAfterMs` while the job is still queued or running. Terminal states add `durationMs` (worker run time, computed from `completedAtEpochMs - startedAtEpochMs`). Completed responses additionally include `result` (the analyzer payload). Top-level fields: `site`, `heroName`, the summary numerics (`handsImported` / `handsAnalyzed` / `handsSkipped` / `decisionsAnalyzed` / `mistakes` / `totalEvLost` / `biggestMistakeEv` -- inlined at the top, NOT nested under a `summary` key), `modelSource` (see the `MODEL_DIR` bullet for the path-vs-masked-form discussion), plus the three nested arrays / objects `warnings` (string array of analyze-stage caveats), `decisions` (top-N flagged-decision objects, sorted by `|evDifference|` descending so the largest EV gaps surface first -- see the `MAX_DECISIONS` env-var bullet below for the configurable cap on N; per-entry fields are `handId` / `street` / `heroCards` / `actualAction` / `recommendedAction` / `actualEv` / `recommendedEv` / `evDifference` / `heroEquityMean`), `opponents` (per-villain rollups, sorted by `handsObserved` descending so the most-frequently-observed opponents surface first -- secondary sort on `playerName` ascending for deterministic tiebreaks -- and capped at the top 5 entries (the cap is HARDCODED at the analyze service, NOT configurable via env var, so a deployment with many villains across a multi-hand history still gets only the top 5 in the response; the full set is still walked for hand-by-hand decision context, just truncated in the per-opponent summary); per-entry fields are `playerName` / `handsObserved` / `archetype` / `hints` array of `{ruleId, text, metrics}` (the `hints` array itself is capped at the top 3 per opponent -- also hardcoded, also not env-tunable -- and entries are in rule-evaluation order rather than confidence-sorted, so the first hints to surface are the first rules to fire in the exploit-hint computation, not necessarily the strongest exploits by deviation magnitude), and `trace` (deep diagnostic snapshot the bundled UI ignores -- present for integration tests and power-user debugging: `trace.request` echoes the parsed request shape including `rawHeroName` / `normalizedHeroName` / `requestedSite` / `handHistoryBytes`; `trace.import` reports auto-detection results -- `handsImported` / `siteResolved` / `heroNameResolved` / `distinctPlayersObserved`; `trace.hands` is a per-hand status array marking each hand as `analyzed` or `skipped` with a `skipReason` / `warning`; `trace.summary` mirrors the top-level summary numerics under a nested-object shape for callers that prefer to read them that way). Failed responses include `errorStatus` (HTTP-equivalent, classified by `JobQueue.classifyAnalysisError` from the error-message prefix): `504` when `error` starts with `analysis timed out after` (the `ANALYSIS_TIMEOUT_MS` ceiling fired and the worker interrupt landed -- shipped frontend prettifies the raw-ms suffix into `Xm Ys` form via `formatDuration` before surfacing to the user, but scripted clients keying on the prefix or `errorStatus` see the verbatim `analysis timed out after Nms` text; parallel translation runs on the hall side per the `/api/playing-hall/jobs/{id}` bullet below); `500` when `error` starts with `analysis failed:` (a backend exception was caught and re-emitted with that prefix from the analyze service or the JobQueue's `NonFatal` handler); `400` for everything else -- in practice, the parse-stage messages the analyze service emits BEFORE the EV computation: `could not auto-detect hand-history site from: <first non-empty line>` (no site was explicitly set and the file's first non-empty line didn't match a PokerStars / Winamax / GGPoker header marker -- the user typically uploaded a non-hand-history text file), and `no PokerStars hands found in input` / `no Winamax hands found in input` / `no GGPoker hands found in input` (the explicit or auto-detected site had no matching headers in the file body, typically the user picked the wrong site or pasted from the wrong export). The full `error` text always lands in the JSON body alongside `errorStatus` so a frontend can decide whether to surface the message verbatim (the parse-stage 400s are operator-readable and useful to display directly) or to map common cases through a friendlier lookup table. **The parse is all-or-nothing per submission**: a single malformed hand block (truncated mid-action, missing summary line, invalid action sequence, etc.) in a multi-hand file fails the entire upload with that hand's specific per-hand parse error message (`HandHistoryImport.parseSite` collects the first `Left` and returns it -- there's no partial-success response containing only the well-formed hands). Users hitting this can split the file around the problem hand and re-upload each half separately; an operator triaging "I uploaded a 500-hand file and got one parse error" support ticket should suggest exactly that. `404` if the job is unknown (never existed, expired off the 15-min terminal-job retention, or — under platform-user auth — was submitted by a different user). Rate-limited as JobStatus.

Playing Hall simulation:

- `POST /api/playing-hall` — submit a hall simulation. All JSON body fields are optional; omitted values fall back to documented defaults. Numeric ranges are enforced server-side with `400` on out-of-range values:
  - `hands` (1..5000, default 240), `tableCount` (1..24, default 2), `playerCount` (2..9, default 6)
  - `heroStyle` (`adaptive`/`gto`/`strategic`, default `adaptive`)
  - `heroPosition` (`SmallBlind`/`BigBlind`/`UTG`/`UTG1`/`UTG2`/`Middle`/`Hijack`/`Cutoff`/`Button`, default `Button`)
  - `gtoMode` (`fast`/`exact`, default `exact`)
  - `villainPool` (array of 1..8 entries from `nit`/`tag`/`lag`/`station`/`callingstation`/`maniac`/`gto`, each entry capped at 32 chars; default `[tag, gto]`)
  - `heroExplorationRate` (0.0..1.0, default 0.0), `raiseSize` (0.25..20.0, default 2.5)
  - `bunchingTrials` (1..600, default 40), `equityTrials` (1..6000, default 240)
  - `learnEveryHands` (0..5000, default 0), `learningWindowSamples` (0..500000, default 200)
  - `seed` (any Long, default 42), `saveReviewHandHistory` (bool, default false), `fullRing` (bool, default false)

  Rate-limited as Submit; admission shares the same `MAX_CONCURRENT_JOBS` / `MAX_QUEUED_JOBS` budget as hand-history analysis.
- `GET /api/playing-hall/jobs/{jobId}` — poll job status. Returns `200` with `status=queued` / `running` / `completed` / `failed` / `cancelled` (cancelled is reachable only via `DELETE` below; analyze jobs share the rest of the state set but never reach cancelled), the universal fields `jobId` / `statusUrl` / `submittedAtEpochMs` / `startedAtEpochMs` / `completedAtEpochMs` (the latter two are `null` until the worker reaches each transition), and `pollAfterMs` while the job is still queued or running. Terminal states add `durationMs` (worker run time; on cancelled responses, only present when the worker had already started before the interrupt landed). Completed responses additionally include `result` (the hall payload), shaped as two top-level objects. `result.request` echoes the 16 submitted-config fields (`hands` / `tableCount` / `playerCount` / `heroStyle` / `heroPosition` / `gtoMode` / `villainPool` / `heroExplorationRate` / `raiseSize` / `bunchingTrials` / `equityTrials` / `learnEveryHands` / `learningWindowSamples` / `saveReviewHandHistory` / `fullRing` / `seed`) for self-describing replay -- a scripted client persisting the result can re-derive the exact run config from `result.request` alone, no separate input log needed. `result.summary` carries the actual outputs across six conceptual groups: **core counters** (`handsPlayed`, `tableCount`, `playerCount`); **hero P&L** (`heroNetChips`, `heroBbPer100`, `heroWins`, `heroTies`, `heroLosses`); **action mix** (`actionCounts` as a `Fold/Check/Call/Raise → count` map); **model + output** (`retrains` count, `modelId` string, `outDir` absolute path, `outputFiles` array of absolute paths to whichever of `hands.tsv` / `learning.tsv` / `training-selfplay.tsv` / `ddre-training-selfplay.tsv` / `review-upload-pokerstars.txt` actually got written this run); **exact-GTO cache instrumentation** (`exactGtoCacheHits` / `exactGtoCacheMisses` / `exactGtoCacheHitRate` plus per-provider breakdowns `exactGtoSolvedByProvider` and `exactGtoServedByProvider` as `provider → count` maps); **per-villain + per-hand series** (`perVillainNetChips` map of `villainName → netChips`, `perHandHeroNet` array of per-hand hero net-chip deltas used by the bundled UI for the cumulative-chips chart, `heroDecisionEquities` array of mean-equity values at each decision point used for the equity-histogram chart); and **Phase-2 overlay diagnostics** (`overlayStats` -- `null` when the strategic overlay was inactive, otherwise an object with `decisions` / `overlayChangeRate` / `vetoRate` / `decisionsWithVeto` / `totalVetoedActions` / `meanLatencyMs` / `p95LatencyMs` / `p99LatencyMs` / `actionDistribution`). Failed responses include `errorStatus` (HTTP-equivalent, classified by `JobQueue.classifyPlayingHallError` from the error-message prefix, parallel to the analyze classifier): `504` when `error` starts with `playing hall timed out after` (the `PLAYING_HALL_TIMEOUT_MS` ceiling fired and the worker interrupt landed -- shipped frontend prettifies the raw-ms suffix into `Xh Ym Zs` form via `formatDuration` before surfacing to the user, but scripted clients keying on the prefix or `errorStatus` see the verbatim `playing hall timed out after Nms` text); `500` when `error` starts with `playing hall failed:` (the hall backend caught a non-fatal exception at `TexasHoldemPlayingHall` and re-emitted with that prefix; same shape as analyze's `analysis failed:`). The 400 bucket in `classifyPlayingHallError` is defensive and currently unreachable -- the hall backend's only Left value is the `playing hall failed:` prefix, so any post-classifier `errorStatus` is one of `500` / `504` in practice. Cancelled responses include partial `result` when the worker captured it before interrupt. `404` if the job is unknown (never existed, expired off retention, or owned by a different user under platform-user auth). Rate-limited as JobStatus.
- `DELETE /api/playing-hall/jobs/{jobId}` — request cooperative cancellation of an in-flight Playing Hall job. Returns `200` with a minimal body `{"jobId":"<id>","status":"cancelled"}` while the job is still cancellable (queued or running). The cancellation response is intentionally minimal -- it carries NO `result`, no `submittedAtEpochMs` / `startedAtEpochMs` / `completedAtEpochMs`, and no `durationMs`. A client that wants to know whether the worker captured any partial data, OR the exact wall-clock duration before the interrupt landed, OR the final terminal state (which is `cancelled` after the worker has unwound, but the cancel acknowledgment fires synchronously before the worker even sees the cancel flag), must follow up with a GET on the same `/api/playing-hall/jobs/{jobId}` status URL -- that response carries the full poll-shape including any partial `result` the worker captured before exit (per the bullet above). `409` if the job already reached a terminal state (completed / failed / cancelled — re-DELETEing an already-cancelled job returns 409, not 200), `404` if unknown / expired / cross-user. Rate-limited as JobStatus.

Platform-user auth (when `USER_STORE_PATH` is set):

- `GET /api/auth/me`, `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `POST /api/auth/profile`
- `POST /api/auth/register` and `POST /api/auth/login` are rate-limited as Auth (see `RATE_LIMIT_AUTH_PER_MINUTE` below; default 10/min/IP). Throttles credential-stuffing and slow-disk-fill registration abuse without burning a PBKDF2 verify per attempt. `/me`, `/logout`, and `/profile` are not rate-limited, but for different reasons: `/logout` and `/profile` require an authenticated session (`AuthRequirement.Required`), so the same-IP flood vector is bounded by sign-in cost. `/me` is open to anonymous callers by design (`AuthRequirement.Optional` -- the frontend probes it at boot to discover the deployment's auth mode AND the current session state, so it must work without a session); the lack of a bucket is justified by the cheap-read nature of the endpoint (in-memory state, no PBKDF2, no disk I/O), and an attacker who floods `/me` only pays for JSON-serialization CPU rather than the credential-cost work the auth bucket exists to throttle.
- `POST /api/auth/register` body is `{email, password, displayName?}`; the response is `201 Created` with the same auth-state shape as `/api/auth/me` below. `POST /api/auth/login` body is `{email, password}` (a `displayName` on a login request is silently ignored -- the field is only consumed by register, and updates after sign-in go through `POST /api/auth/profile`). Fields are length-capped server-side: email at 254 chars (RFC 5321 §4.5.3.1.3), password at 10..256, displayName at 96. When `displayName` is omitted or trims to empty at register time, the server auto-fills it from the email's local-part (e.g. `alice@example.com` → `alice`); the literal fallback `SICFUN User` only fires when the local-part is itself empty, which `validateEmail` already rejects, so that string is effectively unreachable. The user can change `displayName` later via `POST /api/auth/profile`. All three platform-user auth POSTs (`/register`, `/login`, `/profile`) ALSO cap the request body at a hardcoded **16 KiB** (16384 bytes) -- separate from the analyze + hall routes' `MAX_UPLOAD_BYTES` cap (default 2 MiB), much tighter to bound the credential-stuffing attack surface. Over-size requests bounce with `413` and the literal message `request body exceeds max upload size of 16384 bytes` (operator-readable but does NOT distinguish auth-cap vs analyze/hall-cap -- the message is shared across both code paths). The 16 KiB ceiling is operationally invisible because the legitimate `{"email","password","displayName"}` body JSON-encodes to well under 1 KiB even at the field caps (254+256+96 = 606 chars of payload + JSON overhead), so the cap is two orders of magnitude of headroom over real traffic. A scripted client hitting 413 on an auth endpoint with a multi-KiB body is almost certainly malformed -- typically a base64-blob accidentally pasted into the password field, a Unicode normalization issue inflating visible-character counts, or a non-`{email,password,...}` JSON shape (e.g., an array submission) that the parser would reject anyway.
- `GET /api/auth/me` returns the live auth-state JSON: `authenticationEnabled` (bool), `authenticationMode` (`users` / `basic` / `none`), `authenticated` (bool), `allowLocalRegistration` (bool — frontends gate the Register button on this), `providers` (array of auth-provider summaries; each entry is `{id, displayName, kind, startPath}` where `kind` is `password` for the always-present `local` entry (`displayName: "Email and password"`, `startPath: null` -- email/password sign-in goes through the auth form rather than a separate route) and `oidc` for each configured OIDC provider (`displayName` from the provider's own config, e.g. `"Google"`; `startPath` the `/api/auth/oidc/<id>/start` route the frontend Continue-with-X link targets). The shipped frontend keys on `id` to find a specific provider (e.g. `google`) and uses `startPath` directly to render the Continue-with-X anchor; `displayName` and `kind` are exposed for richer multi-provider UIs that haven't shipped yet. Array order is fixed and deterministic: the `local` entry comes FIRST (always present in platform-user mode), followed by each configured OIDC provider in the order they were declared at startup (currently just `google` when `GOOGLE_OIDC_*` is set; a future multi-provider deployment preserves the config-file declaration order, NOT alphabetical -- unlike `linkedProviders` on the `user` object below, which IS alphabetically sorted). A frontend that wants a different order should sort post-receive; the server-side default leads with `local` because email/password is the most-common-case sign-in path and naturally belongs at the top of a sign-in chooser.), `user` (the signed-in account view with `userId` / `email` / `displayName`, plus optional `heroName` / `preferredSite` / `timeZone` / `avatarUrl` and the `linkedProviders` array naming all provider ids linked to the account (alphabetically sorted, distinct -- includes the literal `local` value for a password-registered user, plus any OIDC provider id like `google` for an OIDC-linked user; the two are mutually exclusive on a given account because the local-vs-OIDC email-collision rule above blocks mixing); `null` when not signed in), and `csrfToken` (string the client must echo in `X-CSRF-Token` for state-changing requests under platform-user auth; `null` outside platform-user mode or when no session is on the request). The exact same shape is returned by every state-changing platform-user response: successful `POST /api/auth/register` (`201`) carries the newly-created session's state, `POST /api/auth/login` (`200`) the just-established session, `POST /api/auth/logout` (`200`) the post-signout degenerate state (`authenticated: false`, `user: null`, `csrfToken: null` — useful for the client to reset local state without an extra `/me` round trip), and `POST /api/auth/profile` (`200`) the same state with the `user` field reflecting the newly-saved profile values (the `csrfToken` in the response is the SAME token the client already has from login -- profile save does NOT mint a new session or rotate the CSRF token; the field is included for response-shape uniformity with `/me` / `/login` / `/register` / `/logout`, not because clients need to refresh it -- if a client tracks a single csrfToken across the session lifetime, it can ignore the profile response's csrfToken field with no functional impact; the only state-changing responses that actually rotate the token are `POST /api/auth/login` / `POST /api/auth/register` / the OIDC callback, all of which create a fresh session record). Under basic-auth and no-auth modes `/api/auth/me` returns a degenerate form of the same seven-field shape, NOT a four-field subset: `authenticationEnabled` (`true` under basic auth -- the server enforces an `Authorization:` header even though the platform-user paths are off -- `false` under no-auth), `authenticationMode` (`basic` or `none` accordingly), `authenticated: false` (no platform-user session concept), `allowLocalRegistration: false` (the register endpoint is `404` outside platform-user mode anyway), `providers: []`, `user: null`, `csrfToken: null`. The same field set means a frontend can key on `authenticationMode` to switch UI modes (gating the local register/login forms behind `mode === "users"` only, showing a generic "managed by upstream" panel for `"basic"`, and an open-access panel for `"none"`) from a single probe of the same endpoint -- the shipped frontend does exactly that.
- Optional OIDC start/callback at `GET /api/auth/oidc/{provider}/start` and `GET /api/auth/oidc/{provider}/callback` (e.g. `GET /api/auth/oidc/google/callback`) when the matching `*_OIDC_*` settings are configured. Both are GET-only top-level redirects (the user agent receives a `302 Location: <provider>` from `/start`, the provider sends the user back to `/callback?state=...&code=...` via a navigation, and `/callback` issues a final `302` to `/?auth=success` or `/?auth_error=...`). `OPTIONS` returns `204 No Content` with `Allow: GET, OPTIONS` for capability discovery -- this is the 204-no-body shape, matching the static-asset handler used for the upload UI itself. The JSON-API routes elsewhere on this server (POST `/api/auth/register` / `/api/auth/login` / `/api/auth/logout` / `/api/auth/profile`, plus the analyze + playing-hall submission / status / cancel endpoints) take the alternative 200-with-`{"allow":"<verbs>"}`-body shape for OPTIONS, which RFC 7231 sec 4.3.7 also permits. OIDC + static-asset routes pick 204 because there's no meaningful body beyond the `Allow` header; JSON-API routes pick 200 with a body for uniformity with the rest of their JSON-shaped responses. Both forms carry the same `Allow:` header so capability-discovery tools (curl `-X OPTIONS`, OpenAPI scanners, etc.) get equivalent information either way. Other non-GET methods on `/start` and `/callback` return `405 Method Not Allowed` with the same `Allow: GET, OPTIONS` header.
- The `register` / `login` JSON responses include a `csrfToken` field. State-changing routes under platform-user auth (`POST /api/auth/logout`, `POST /api/auth/profile`, `POST /api/analyze-hand-history`, `POST /api/playing-hall`, `DELETE /api/playing-hall/jobs/{id}`) require this token in the `X-CSRF-Token` request header in addition to the session cookie; missing or mismatched values produce `403` `"missing or invalid csrf token"`. Scripted clients can either re-call `GET /api/auth/me` to refresh the token or stash it from the original login response. The OIDC callback also issues a fresh token via the same response shape.

## Core Configuration

Edit `conf/hand-history-web.env` instead of hard-coding long-lived settings into service command lines.

Common settings:

- `HOST` / `PORT`: bind address and port (default `127.0.0.1` / `8080`). HOST values: `127.0.0.1` (loopback, default; safe for single-host deployments), `0.0.0.0` (all IPv4 interfaces -- requires one of the auth modes configured or the explicit `ALLOW_UNAUTHENTICATED_PUBLIC_BIND=true` override per the auth-modes bullet below), a specific LAN IP (bind to one interface on a multi-homed host), or the IPv6 equivalents `::1` (loopback) / `::` (all IPv6 interfaces). HOST is NOT pre-validated at config time -- a typo, unresolvable hostname, or interface not present on this host surfaces at JDK `HttpServer.create` time as a `java.net.BindException` and stops the launcher with the JDK exception message in the startup-failure output. PORT accepts any integer but the JDK `InetSocketAddress` constructor throws `IllegalArgumentException` for values outside `0`-`65535`. PORT=`0` is a SPECIAL CASE: the JDK asks the OS to assign an ephemeral port at bind time, the server starts successfully, and `/api/health.port` / `/api/ready.port` / the startup-banner `port=<N>` log field report the OS-assigned port -- useful for test harnesses that need to avoid hardcoded ports, less useful in production where a stable port is what reverse proxies and service managers expect. Privileged ports (`1`-`1023` on Unix) require running the JVM as root or granting `cap_net_bind_service`; on Windows any free port works. **Port-collision pitfall**: a `BindException: Address already in use` at startup means another process (often a previous instance of this app still draining after a too-quick restart, or an unrelated app holding the port) has the socket -- check via `netstat -ano | findstr :<port>` on Windows or `ss -tlnp | grep :<port>` on Linux, then stop the conflicting process (or wait for its `SO_REUSEADDR` window to expire, typically 30-60 sec after a clean shutdown) or pick a different PORT.
- `ALLOW_UNAUTHENTICATED_PUBLIC_BIND` (default `false`): explicit override for non-loopback binds without auth on a trusted private network. The server otherwise refuses to bind to a non-loopback host without one of the auth modes configured, failing startup with `refusing to bind to a non-loopback host without auth; configure BASIC_AUTH_*/USER_STORE_PATH or set --allowUnauthenticatedPublicBind=true / ALLOW_UNAUTHENTICATED_PUBLIC_BIND=true to override for a trusted private network`. **"Loopback" definition** (HandHistoryReviewServerConfig.scala `isNonLoopbackBindHost`): the empty string, `localhost`, `::1`, the verbose IPv6 form `0:0:0:0:0:0:0:1`, OR any IPv4 address in the `127.0.0.0/8` block (i.e., any host whose case-folded form starts with `127.` -- not just `127.0.0.1`). The check strips IPv6 brackets first, so `[::1]` and `::1` are equivalent. Everything else -- a specific LAN IP, `0.0.0.0`, a hostname, IPv6 link-local, etc. -- is considered non-loopback and triggers the auth-required gate. Worth noting because operators sometimes pick `127.0.0.5` expecting a different-from-loopback behavior to get a separate-bind-slot for testing; the auth gate treats it as loopback the same as `127.0.0.1`, so no auth is required (and the bind succeeds without any override).
- `STATIC_DIR`: directory served as the upload UI (default `docs/site-preview-hybrid` in source mode; `static/` relative to the bundle root after `release-hand-history-web.ps1` packages it). Override only when you've copied or modified the static assets to a non-standard location. The path is NOT validated at startup -- the existence check runs per request inside `StaticAssetsHandler` via `Files.exists`, so a misconfigured `STATIC_DIR` (path typo, relative-path-vs-cwd mismatch, partially-extracted bundle missing the static subdirectory) lets the server start successfully and `/api/health` returns `200` as usual, but every `GET /` and `GET /<asset>` returns a generic `404 not found`. Triage shortcut for "the upload UI doesn't load but the health probe is green": curl the server's bound host:port and check whether `GET /` returns 200 with `Content-Type: text/html` (correct) or 404 with `Content-Type: text/plain` body `"not found"` (STATIC_DIR is wrong). Also check the boot-time log line `serving static site from <resolved-absolute-path>` (logged by `HandHistoryReviewServer.scala` immediately after the HTTP server binds -- this is a SEPARATE line from the longer `startup complete host=... port=... modelSource=... maxUploadBytes=...` banner, which does NOT carry the staticDir field; grep `serving static site from` to find it) -- the launcher logs the resolved absolute path so an operator can verify the path it actually picked against the path they meant to configure.
- `MODEL_DIR`: optional path to a packaged action-model artifact directory. When set, the analyze backend loads it for EV-gap and recommended-line scoring; when unset, the backend falls back to a uniform action model and the analyze results lose their model-specific edge (recommendations are correct in shape but undifferentiated). The `modelSource` string is surfaced in three places with two distinct shapes: `/api/health` and `/api/ready` use the **masked** form `"configured artifact dir"` vs `"uniform fallback"` so dashboards can flag instances accidentally running without their intended model without tying alert rules to the operator's filesystem layout (a parallel boolean field `modelConfigured` -- `true` when `MODEL_DIR` is set, `false` otherwise -- ships in the same `/api/health` response so a dashboard preferring a `bool == false` alert condition over a string compare can use either; `modelConfigured` is `/api/health`-only and is NOT echoed by `/api/ready`); the analyze response's `result.modelSource` field AND the startup-banner log line's `modelSource=` field (the latter listed in the `%20`-escape inventory below) both use the **unmasked** form -- the absolute normalized path of `MODEL_DIR` (e.g. `C:\Program Files\sicfun-model\v2`) when set, `"uniform fallback"` when not. The bundled frontend renders the unmasked form verbatim under the analyze result's "Model" summary card so a power user can confirm which artifact version produced their recommendations. Scripted clients keying off `result.modelSource` should expect the path form -- it's stable across responses for one server boot but is operator-controlled filesystem layout, so prefer matching by basename or prefix rather than the full string.
- `MAX_UPLOAD_BYTES`: upload cap in bytes (default `2097152`, i.e. 2 MiB; applies to both `/api/analyze-hand-history` and `/api/playing-hall` request bodies). The frontend probes `/api/health` at page load and adopts this value as its client-side file-size check, so raising the server cap automatically raises what the upload form accepts without a frontend rebuild.
- Analyze-backend tuning knobs (per-instance defaults the `HandHistoryReviewService` worker uses on every `/api/analyze-hand-history` job; not surfaced via `/api/health`):
  - `SEED` (Long, default `42`): RNG seed for the analyze backend's Monte Carlo equity + bunching trials. Same seed + same input + same trial counts → same EV-gap output, so this is useful for reproducing an exact analyze result across deployments or across debugging runs. Different from the `seed` field in the Playing Hall job body, which is the hall-runner's own per-job seed (the two RNGs are independent).
  - `BUNCHING_TRIALS` (Int, default `200`): Monte Carlo samples for the bunching correction (the equity adjustment that accounts for "the hands the folded villains were holding aren't in the remaining deck"). Raise for tighter equity estimates in spots where bunching matters most (deep-stacked, multi-way, late-street); lower for faster per-decision processing on a CPU-constrained host. The default 200 is a reasonable compromise for the 2-min `ANALYSIS_TIMEOUT_MS` ceiling.
  - `EQUITY_TRIALS` (Int, default `2000`): Monte Carlo samples per equity call (one call per decision per opponent-range candidate). The biggest knob for analyze-CPU spend: raising to 5000 roughly doubles per-decision processing time but tightens equity confidence by ~√2.5; lowering to 500 cuts cost ~4× at the price of noisier EV gaps that may flip the "biggest mistake" ranking between runs of the same file.
  - `BUDGET_MS` (Long, default `1500` ms): per-decision EV-computation time budget. The analyzer aborts the Monte Carlo loop when this budget is exhausted, returning whatever estimate it has at that point rather than burning the full `EQUITY_TRIALS` count on a pathologically-slow hand (e.g., 9-way multi-street with complex effective-stack interactions). For typical 6-max heads-up-by-the-river hands the budget is rarely tight; raise it only if you're seeing rough EV estimates on specific hand archetypes in the worst-case branch of `trace.hands[i].warning`.
  - `MAX_DECISIONS` (Int, default `12`): top-N flagged decisions returned in the analyze response's `result.decisions` array, sorted by `|evDifference|` descending (largest gaps first). Raise to surface more of the long tail (e.g., 30 for a thorough session review); lower to focus the UI on the few biggest gaps (e.g., 5 for a "what hurt me most" dashboard). The truncation happens server-side, so a lower cap also cuts response-body size and JSON-render CPU on the frontend.
- `ANALYSIS_TIMEOUT_MS`: per-job timeout for `/api/analyze-hand-history` jobs (default `120000`, i.e. 2 min); `0` disables it. The shipped frontend probes `/api/health.analysisTimeoutMs` at boot and rolls it into the same `max(16 min default, server timeout + 1 min slack)` poll deadline described under `PLAYING_HALL_TIMEOUT_MS` below, so raising this knob does NOT need a frontend rebuild.
- `PLAYING_HALL_TIMEOUT_MS`: per-job timeout for `/api/playing-hall` jobs (default `900000`, i.e. 15 min); `0` disables it. The shipped frontend probes `/api/health.playingHallTimeoutMs` at boot and extends its poll deadline to `max(16 min, server timeout + 1 min slack)`, so raising this knob on the server side automatically extends the frontend's patience without a frontend rebuild. `0` (disabled) on the server side falls back to the 16-min frontend default — the page won't poll indefinitely on a bottomless job.
- `MAX_CONCURRENT_JOBS` / `MAX_QUEUED_JOBS`: admission limits shared across both job stores. Defaults derive from host CPU: concurrent is `clamp(availableProcessors - 1, 1, 4)` (so a 2-core host gets 1, an 8-core host gets 4, and a 32-core host still gets 4 — the cap stops the worker pool from contending with the JVM's own threads), and queued is `max(8, concurrent * 8)`. A small dual-core deployment lands at 1 concurrent + 8 queued; a typical 8-core lands at 4 + 32. Both must be strictly positive (`> 0`); startup fails fast with `--maxConcurrentJobs must be positive` / `--maxQueuedJobs must be positive` on a zero or negative value. **Shared-pool consequence**: the analyze and Playing Hall job stores both submit `Runnable`s into the SAME `ThreadPoolExecutor` (one pool, not two), so a long-running Playing Hall job consumes one of the `MAX_CONCURRENT_JOBS` worker slots and blocks an analyze submission from starting if the rest of the pool is also busy with hall jobs. The bounded `ArrayBlockingQueue` feeding the pool is similarly shared FIFO -- a queued hall job ahead of an analyze submit in the queue means the analyze waits for that hall to complete its worker slot. Operators serving both flows on the same instance who hit contention pain (analyze submits 503'ing under hall load) should either raise `MAX_CONCURRENT_JOBS` so saturation is rarer (the default-4 cap on a 8-core host is sized for a single-user / small-team deployment; a multi-user team can usefully run 8 or more, accepting that the worker pool contends with the JVM's own internals above that), OR front the deployment with two separate instances on different ports + a path-routed reverse proxy that sends `/api/analyze-hand-history*` to one and `/api/playing-hall*` to the other (each instance then gets its own non-contended pool budget).
- `SHUTDOWN_GRACE_MS`: graceful shutdown budget in milliseconds (default `5000`, i.e. 5 sec). Total wall-clock window the server has to drain on SIGTERM / Ctrl-C / JVM shutdown hook. The budget composes across three sequential phases under a single deadline (computed once at shutdown start, NOT re-applied per phase): the JDK `HttpServer`'s in-flight HTTP request drain → the analysis-timeout executor wind-down → the analysis worker pool wind-down. Each phase claims the wall-time REMAINING vs the shared deadline, so a fast first phase leaves more for the next -- if HTTP requests drain in 100 ms, the analysis executor still gets ~4.9 s to finish in-flight jobs. Pre-fix versions of this code passed the full budget to every phase, which extended the worst-case shutdown to 4×grace; the current code emits the actual `httpDrainSeconds=<N>` value in the `shutdown requested` log line so an operator can verify the composition empirically on the most recent restart. Exceeded budget: the JVM force-exits, in-flight analyze + hall jobs are lost (pending `Runnable`s in the worker pool are dropped, the HTTP server stops listening immediately). For deployments where `ANALYSIS_TIMEOUT_MS` or `PLAYING_HALL_TIMEOUT_MS` is raised well above default (analyze runs measured in minutes, hall runs over 15 min), raise this knob proportionally so a graceful restart can finish mid-flight work rather than forcibly terminating it; the default 5 s assumes the typical sub-second analyze completion + the default 15 min hall ceiling being mid-run rarely enough that the loss is acceptable.
- `DRAIN_SIGNAL_FILE`: optional path to a sentinel file the operator creates to pre-drain the instance before SIGTERM. When the file EXISTS (contents irrelevant; only `Files.exists` is checked, per readiness probe), the instance enters drain mode: `/api/ready` flips to `503` with `reason=draining`, new submissions to `POST /api/analyze-hand-history` and `POST /api/playing-hall` are admission-rejected with `503` `service is draining`, and `/api/health.drainSignalPresent` reports `true`. The check is lazy and stateless -- no filesystem watcher, no in-memory cache -- so the operator can `touch <path>` to drain and `rm <path>` to undrain at any time without restarting the server; the very next readiness probe reflects the new state. **Rolling-restart pattern**: (1) `touch` the file → reverse proxy / load balancer observes `/api/ready` returning 503 and stops routing new traffic to this instance → in-flight jobs continue completing naturally (drain mode does NOT interrupt them, unlike the `SHUTDOWN_GRACE_MS` budget-exhaustion path which force-drops them on JVM exit); (2) wait for `runningJobs` + `queuedJobs` in `/api/health` to drop to zero; (3) SIGTERM the process → the `SHUTDOWN_GRACE_MS` budget covers the remaining HTTP-drain + executor-wind-down phases described above. `/api/health.drainSignalConfigured` reflects whether the knob is set (independent of whether the file currently exists), so a dashboard can verify the deployment is wired for graceful rolling restarts at all. Without this knob configured, the only drain signal is the JVM shutdown hook itself -- which doesn't pre-stage the load balancer's stop-routing decision, so the worker pool runs at full traffic right up to the SIGTERM moment and any submit that lands in the last few hundred ms before the hook fires races the budget rather than declining cleanly with 503.

Auth modes:

- Basic auth: set `BASIC_AUTH_USER` and `BASIC_AUTH_PASSWORD` (both required together — setting one without the other fails startup with a clear error). The username may not contain `:` (HTTP Basic uses it as the user:password separator per RFC 7617), and both values are trimmed; empty / whitespace-only values are treated as unset (worth noting because a password with intentional leading/trailing whitespace would silently lose those characters at config time -- pick passwords without padding). **WWW-Authenticate realm**: `sicfun-hand-history-review`, sent on `401` responses as the full header `WWW-Authenticate: Basic realm="sicfun-hand-history-review", charset="UTF-8"`. Browser auth popups display the realm as prompt context ("sicfun-hand-history-review wants you to sign in"), and password managers scope saved credentials by `(origin, realm)` pair -- if you want one shared password-manager entry to cover multiple sicfun instances on different hosts/ports, keep this realm string stable across them. The `charset="UTF-8"` parameter signals the server decodes Authorization-header credentials as UTF-8 per RFC 7617 sec 2.1; modern browsers honor it (encoding non-ASCII passwords as UTF-8), older ones default to ISO-8859-1 which still works for ASCII-only passwords. **Credential comparison**: constant-time `secureEquals`, with the username + password results AND-ed via the non-short-circuit `&` operator (NOT `&&`) so both compares always run regardless of the first's outcome -- prevents a timing oracle from distinguishing "wrong username" (only username compared under `&&`) from "right username, wrong password" (both compared), which would otherwise let an attacker enumerate valid usernames over enough probes even when each individual compare is constant-time on its own.
- Platform-user auth: set `USER_STORE_PATH` to the absolute path where the JSON-formatted user store should live. The file does not need to be pre-created -- the server starts with an empty in-memory store when the path doesn't exist yet and creates the file atomically on the first successful registration (or the first OIDC sign-up). The atomic-write strategy writes through a `platform-users-*.json.tmp` temp file in the same parent directory and then `Files.move(... ATOMIC_MOVE)` renames it onto the target path -- so a half-finished write never overwrites the live store. The server falls back to a non-atomic `REPLACE_EXISTING` move on filesystems that don't support atomic rename (rare; mostly some network-mounted exotic FS). A hard-kill (SIGKILL, OOM, power loss) during a write may leave an orphan `platform-users-*.json.tmp` file in the user-store directory; these are harmless to delete and the JVM's normal finally-cleanup removes them on graceful errors. The JSON content carries a top-level `"version": 1` field for future schema migrations (the server currently ignores it on read, accepting whichever shape is present). The parent directory DOES need to exist and be writable by the service account. If the file is present but unreadable (e.g., partial write from a crash that survived as a non-atomic move target, manual edit that broke JSON syntax), startup fails fast with `user store at <path> is unreadable: <ujson parse error>. Back up the file and restore from backup, or remove it to start fresh.` -- the remove-to-start-fresh option drops all stored users so prefer the backup path when one exists.
- `ALLOW_INSECURE_USER_AUTH` (default `false`): explicit override for non-loopback platform-user auth without secure cookies or an HTTPS OIDC callback on a trusted private-network test deployment. The server otherwise refuses to start when `USER_STORE_PATH` is set on a non-loopback host without `USER_AUTH_COOKIE_SECURE=true`.
- Do not enable both at the same time
- For safety, non-loopback binds now require one of those auth modes unless you explicitly set `ALLOW_UNAUTHENTICATED_PUBLIC_BIND=true` for a trusted private network
- For safety, non-loopback platform-user auth also requires `USER_AUTH_COOKIE_SECURE=true` unless you explicitly set `ALLOW_INSECURE_USER_AUTH=true` for trusted private-network testing
- When `USER_AUTH_COOKIE_SECURE=true` the session cookie is emitted with the RFC 6265 `__Host-` prefix (`__Host-sicfun_session`) so the browser also blocks a sibling subdomain from overwriting or planting the session cookie. Operator-side log greps and proxy ACLs should account for both `sicfun_session` (insecure mode) and `__Host-sicfun_session` (secure mode). The full session-cookie attribute set is `Path=/; Max-Age=<USER_AUTH_SESSION_TTL_MS/1000>; HttpOnly; SameSite=Lax` plus `Secure` when cookie-secure is on -- the same defense-in-depth shape as the OIDC state cookie, with two differences: the session cookie's `Max-Age` is set to `USER_AUTH_SESSION_TTL_MS / 1000` (default 43200 sec = 12h) rather than the OIDC state cookie's hardcoded 600 sec (10 min) cap, and the session cookie's `Max-Age` is set ONCE at login / register / OIDC-callback and is NOT refreshed by subsequent authenticated requests -- so the cookie expires at exactly `loginTime + ttlMs` regardless of activity (per the `USER_AUTH_SESSION_TTL_MS` bullet above; only the server-side record slides, the cookie itself does not).
- `USER_AUTH_COOKIE_SECURE` defaults to `false` so loopback testing over plain HTTP works (a `Secure` cookie would be discarded by the browser on `http://127.0.0.1`). The non-loopback bind check above flips this knob to required-true at startup so internet-facing deployments don't accidentally ship plain-HTTP cookies.
- `USER_AUTH_MAX_USERS` (default `100000`) caps the total number of registered users. Once reached, further registration attempts return `400` with `"registration is temporarily unavailable"`. Defends against slow disk-fill via public-registration abuse (the auth rate-limit alone caps in-flight attempts at 10/min/IP, but without a per-store cap a persistent bot can still grow the JSON file unbounded over days/weeks). Surfaced in `/api/health` as `userAuthMaxUsers` so dashboards can show "users used / max" and alert when capacity is being approached.
- `USER_AUTH_ALLOW_REGISTRATION` (default `true`): when `false`, `POST /api/auth/register` returns `400` with `"local registration is disabled"` regardless of the `USER_AUTH_MAX_USERS` cap. Use this for closed-registration deployments where new accounts come in only via OIDC sign-up; existing local users can still sign in via `POST /api/auth/login` -- the gate is on REGISTRATION, NOT authentication. OIDC sign-up is still allowed because it doesn't go through `/api/auth/register` (it lands via `/api/auth/oidc/<provider>/callback`'s `upsertOidcIdentity` path, which has its own user-store cap check but no `allowLocalRegistration` gate). **Startup-failure interaction**: the server refuses to start when `USER_AUTH_ALLOW_REGISTRATION=false` AND no OIDC provider is configured -- fails fast with `user auth requires at least one sign-in method`, because that combination would leave users with no way to onboard new accounts. There is NO operator-only back door that bypasses the gate -- `PlatformUserAuth.UserStore.registerLocal` enforces the `allowLocalRegistration` check internally (grep for `if !config.allowLocalRegistration then Left("local registration is disabled")`) regardless of caller, so even a future in-process admin route that called the service method directly would still be blocked. To onboard a user when the public registration form is locked, configure OIDC (most operator-friendly), OR temporarily flip `USER_AUTH_ALLOW_REGISTRATION=true`, have the user register, then flip it back to `false`. The `/api/auth/me` response surfaces the current value as `allowLocalRegistration: <bool>` so the frontend disables the Register button when it's `false` (the shipped UI also adds an `aria-disabled="true"` and a hover tooltip `Registration is disabled on this deployment` so the user sees WHY the button is grayed out, not just THAT it is).
- `USER_AUTH_SESSION_TTL_MS` (default `43200000`, i.e. 12 hours): TTL for both the server-side session record AND the session cookie's `Max-Age`. The mechanics are subtly two-layer and worth understanding before sizing this knob: **server-side record slides** -- every successful `resolveSession` (i.e., every authenticated request whose cookie resolves to a live record) refreshes the record's `expiresAtEpochMs` to `now + ttlMs`, so an actively-used session never expires server-side and the periodic in-memory purge sweep leaves it alone; **cookie Max-Age is FIXED from login time** -- the `Max-Age` attribute on the `__Host-sicfun_session` / `sicfun_session` cookie is set ONCE at login (or register / OIDC-callback) to `ttlMs`, subsequent authenticated requests do NOT re-emit `Set-Cookie`, so the browser-side cookie expires at exactly `loginTime + ttlMs` regardless of how active the user was in the interim. After that point the browser stops sending the cookie and the next request 401s with `reason=session-missing-or-invalid` because the server gets no cookie to resolve. The effective maximum session lifetime is therefore `ttlMs` FROM LOGIN TIME, NOT "indefinite as long as the user is active" -- a user who logs in at 9am with the 12h default is auto-signed-out at 9pm regardless of how busy they were, and needs to re-authenticate. The sliding server-side record only matters for the idle-user case (idle for the full ttlMs without any request → record expires → 401 even if the cookie were somehow still valid). Shorter TTLs trade convenience for tighter post-leak windows; longer TTLs trade exposure for less re-auth friction. **Worst-case-attacker caveat**: the "post-leak window" framing above is accurate for a browser-bound attacker (where browser cookie semantics enforce the FIXED `Max-Age` ceiling), but a `curl` / scripted client sending the leaked token directly in a `Cookie:` header bypasses cookie-expiry rules entirely, and every successful request refreshes the server-side record via the sliding `resolveSession` so the leaked token has effectively unbounded lifetime under the natural-expiry path. The ONLY reliable upper bound on a leaked-token's lifetime under platform-user auth is explicit revocation, which has three paths -- and an operational asymmetry worth understanding: (1) **user OIDC re-auth** (the OIDC `/callback` handler revokes any pre-existing session on the same request; see the OIDC bullet above) -- this is the cleanest path; (2) **user-initiated logout** via the bundled UI's Sign Out button or a direct `POST /api/auth/logout` from the user's authenticated session (requires the user's session cookie + CSRF token, so an OPERATOR cannot unilaterally invoke it from outside -- treat as "ask the user to sign out from any device they still trust"); (3) **operator-initiated server restart** -- the nuclear option that drops EVERY in-memory session record, signing out all current users and forcing fleet-wide re-auth. **LOCAL-password caveat**: a user re-signing in via the local password form does NOT revoke pre-existing sessions, because `handleAuthLogin` returns `409 "already signed in"` when the request carries a valid session cookie -- a leaked-but-still-valid token blocks the legitimate user from minting a fresh session via the auth form, so the OIDC-revoke-on-callback path is the operator-relevant difference between the two auth flows when triaging a suspected leak. Treat re-auth via OIDC as the incident-response default, server restart as the fallback when OIDC isn't configured or the user is unreachable, and the natural-expiry path as not-a-bound-at-all under a determined attacker. Operators who want a true browser-side sliding window (cookie Max-Age refreshed on every authenticated response) would need a code change to re-emit `Set-Cookie` from `/api/auth/me` / `/api/auth/profile` / the analyze + hall poll endpoints; the current architecture deliberately keeps the session cookie a single login-time artifact to avoid the race between re-emit and revoke and to keep the cookie's lifecycle reasoning simple.
- **No password-reset flow exists.** There is no `/api/auth/reset` endpoint, no email-verification mechanism, no out-of-band recovery path -- the platform-user store is intentionally minimal. When a user reports a forgotten password, the operator-side options are: (a) ask the user to register a fresh account under a different email (their old record stays in the store but is unreachable to them), (b) configure Google OIDC and have the user sign in via that path (the OIDC-vs-local-password collision applies if the OIDC email matches the old account -- see below), or (c) manually edit `USER_STORE_PATH` to remove the user's record and let them re-register with the same email. Option (c) is the most direct: stop the service, find the user's record by `email` field in the JSON, delete it, restart. The user loses any saved profile fields (`displayName` / `heroName` / `preferredSite` / `timeZone`) since those live in the same record. If the operator runs SICFUN for a single trusted user / small team where forgotten passwords are rare, this manual triage is acceptable; for a larger user base, deploy OIDC so the provider handles recovery.

Optional OIDC:

- Set `GOOGLE_OIDC_CLIENT_ID`, `GOOGLE_OIDC_CLIENT_SECRET`, and `GOOGLE_OIDC_REDIRECT_URI`. OIDC layers on top of platform-user auth so `USER_STORE_PATH` must also be set; otherwise startup fails with `user auth with OIDC requires --userStorePath/USER_STORE_PATH`. All three Google knobs are required together (configuring just one or two also fails at startup). The redirect URI's PATH component must be exactly `/api/auth/oidc/google/callback` (the path the server registers its callback handler on); any other path -- e.g. `https://example.com/oidc-return` -- fails startup with `--googleOidcRedirectUri/GOOGLE_OIDC_REDIRECT_URI path must be '/api/auth/oidc/google/callback'`. Configure the same path in the Google Cloud Console's Authorized Redirect URIs. The Cloud Console OAuth client must ALSO enable the OAuth scopes `openid`, `email`, and `profile` -- the server's `/start` redirect embeds `scope=openid email profile` (literal space-separated) and the callback parses `sub` / `email` / `email_verified` / `name` / `picture` from the userinfo response, all of which require those three scopes. A Cloud Console client missing `email` will complete the user-facing consent screen but fail at the callback step with `?auth_error=Google%20did%20not%20return%20a%20verified%20email%20address%20for%20this%20account` (one of the 13 finishOidc Left values enumerated in the auth.oidc.failure bullet below); the failure is silent from the user's perspective and surfaces only as a generic friendly message + an entry in the `auth.oidc.failure` log -- worth checking the Cloud Console scope list first when triaging that pattern. The redirect URI also sets `access_type=online`, so the server does NOT request offline access / refresh tokens -- a deployment that wants users to stay signed in across long absences should rely on the platform-user session TTL (`USER_AUTH_SESSION_TTL_MS`, default 12h FIXED from login time -- the cookie's `Max-Age` is set ONCE at login and NOT refreshed on activity, so a user is auto-signed-out at exactly `loginTime + ttlMs` regardless of how active they were; only the server-side record slides via `resolveSession`. See the `USER_AUTH_SESSION_TTL_MS` bullet above for the two-layer record-slides-but-cookie-doesn't mechanic.) rather than expecting Google to refresh tokens silently in the background -- the right knob to raise if a longer-stay UX matters more than the post-leak window is `USER_AUTH_SESSION_TTL_MS` itself, not anything OIDC-side.
- **Outbound HTTPS egress requirement**: the server makes outbound `HTTPS` calls to Google's OAuth endpoints during every OIDC `/callback`. Specifically `oauth2.googleapis.com:443` (token endpoint, hardcoded at `PlatformUserAuth.scala`'s `GoogleTokenEndpoint`) and `openidconnect.googleapis.com:443` (userinfo endpoint, `GoogleUserInfoEndpoint`). In a firewalled deployment (corporate egress restrictions, container with strict NetworkPolicy / egress firewall, host with locked-down outbound rules), BOTH endpoints must be reachable from the server -- otherwise OIDC fails at the corresponding step with `auth.oidc.failure ... reason=Google%20OIDC%20exchange%20failed:%20<connect-timeout-or-DNS-error>` (the catch-all branch of the 13-string finishOidc Left set enumerated in the auth.oidc.failure bullet below), the upstream-error suffix typically a JDK `HttpConnectTimeoutException` after the 5-second connect ceiling fires (see the OIDC HTTP-timeouts bullet below for the connect/request budget detail). If you can't grant egress to both Google domains, OIDC sign-in cannot work in this deployment -- fall back to local-password auth (`USER_AUTH_ALLOW_REGISTRATION=true` with `USER_STORE_PATH` configured) or basic auth (`BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD`). Worth noting: the user-agent's outbound traffic to Google during `/start` and the redirect-from-Google during `/callback` are CLIENT-side (the user's browser, not the server), so client-side network restrictions are a separate consideration -- if the user's network blocks Google, the OIDC flow fails before even reaching our server, and no `auth.oidc.failure` log entry appears (the failure shape parallels the "Users report 'Google sign-in fails' but no auth.oidc.failure log entries appear" runbook entry, except the operator's own server isn't the blocker).
- On non-loopback binds, set `USER_AUTH_COOKIE_SECURE=true` and use an `https://...` redirect URI unless you explicitly set `ALLOW_INSECURE_USER_AUTH=true` for trusted private-network testing
- OIDC vs local-password collision: if a user already has a local-password account with email X, an OIDC sign-in returning the same email X is rejected with `?auth_error=an account with that email already exists; sign in with its existing method` (translated to a friendlier message by the bundled UI). The collision is deliberate -- linking the two identities silently would let any party who controls the Google account claim the password user's data, and silently overwriting either way would surprise the user. Operators triaging "OIDC sign-in suddenly stopped working" support tickets should ask whether the user has a prior local-password account on the same email; if so, the user should sign in with their password instead, OR the operator can manually clear the local-password account from `USER_STORE_PATH` (the OIDC flow will create a fresh user record on the next sign-in).
- The OIDC authorization-code flow uses PKCE (Proof Key for Code Exchange, RFC 7636) with the SHA-256 challenge method. At `/start` the server generates a random 32-byte `code_verifier`, derives `code_challenge = BASE64URL(SHA-256(code_verifier))`, embeds the challenge in the redirect URL's `code_challenge` + `code_challenge_method=S256` parameters, and stashes the verifier alongside the `state` token in the in-memory `OidcStateStore`. At `/callback` the server submits the verifier with the authorization-code-for-token exchange; Google rejects the exchange if the verifier doesn't hash to the original challenge. The defense is layered on top of the `state` cookie / store check (covert-redirect / login-CSRF mitigation) -- PKCE additionally protects against an attacker who intercepted the redirect's authorization code (via a logged URL, a leaked Referer header, or a compromised intermediate proxy) but lacks the verifier. Operators don't need to configure anything; PKCE is on by default and not toggleable.
- The server-to-provider HTTP calls (Google's token + userinfo endpoints) carry hardcoded JDK `HttpClient` timeouts: **5 seconds to establish the TCP connection** and **10 seconds end-to-end per request** (token exchange and userinfo each get their own 10-second budget, so a worst-case callback handler holds an executor thread for up to ~20 seconds when both endpoints stall). Without these timeouts the JDK HttpClient blocks indefinitely on a slow / hung provider endpoint, holding a server executor thread per in-flight callback -- enough concurrent stuck callbacks would saturate the worker pool and starve `/api/health`, `/api/auth/me`, and unrelated routes. The 10-second per-call ceiling is well above Google's typical sub-second latency and well below typical browser network timeouts (~5 min), so a user agent never gives up before the server has had a chance to surface a structured failure. When a timeout fires, the user lands at `/?auth_error=Google%20OIDC%20exchange%20failed:%20...` (the `Google OIDC exchange failed: <upstream-message>` variable-content reason enumerated in the auth.oidc.failure bullet under Logs And Observability below), with `<upstream-message>` typically containing the JDK exception text (`request timed out`, `HttpConnectTimeoutException`, etc.). The timeouts are not operator-tunable -- adjusting them requires a source-level change to `PlatformUserAuth.DefaultOidcConnectTimeout` / `DefaultOidcRequestTimeout`.

Rate limiting:

- `RATE_LIMIT_SUBMITS_PER_MINUTE` — cap on analysis/Playing Hall submissions per IP per minute (defaults to `6`; bounds the worker pool against burst-submit abuse without throttling a human operator queuing a handful of files). Under platform-user auth the bucket keys on the signed-in user (`user:<userId>`) instead of the IP, so a noisy authenticated user can't throttle unrelated users on the same NAT -- see the rate-limit `client=` log-line documentation below for the full keying rules.
- `RATE_LIMIT_STATUS_PER_MINUTE` — cap on job-status polls per IP per minute (defaults to `240`; the server-suggested poll cadence is `750 ms` so one tab steady-state polls ~80 times/min, and the 240 cap leaves headroom for ~3 concurrent tabs from the same IP or one tab plus a sidecar monitor). Same per-user keying override as SUBMITS under platform-user auth, so the headroom math is per-signed-in-user there rather than per-IP.
- `RATE_LIMIT_AUTH_PER_MINUTE` — cap on `/api/auth/register` + `/api/auth/login` attempts per IP per minute (defaults to `10`; throttles PBKDF2-cost credential stuffing). Stays IP-keyed across all auth modes because there's no authenticated user yet at the register/login step. Note: OIDC `/api/auth/oidc/<provider>/start` and `/callback` are NOT in this bucket and are not rate-limited in-process at all (they're GET top-level navigations, one per sign-in attempt in normal usage). For `/start`-storm defense rely on upstream proxy throttling; for the misconfigured-provider pattern (steady `/start` with no matching callbacks) watch the `userAuthPendingOidcFlows` field in `/api/health` -- a count well above the steady-state "very small" is the signal.
- All three buckets use a **fixed 60-second window** anchored at each client's first observed request per bucket (not a sliding window). Operationally this means a client can burst up to ~2× the per-minute limit right at a window boundary -- six submits between `T+55s` and `T+60s` plus six more in the new window starting around `T+61s` both go through and the client only sees `429` from `T+62s` onward. The fixed-window choice keeps the in-process limiter to a single `ConcurrentHashMap.compute` per request; if you need true sliding-window smoothing for fleet-wide burst control, do it at the upstream proxy (nginx `limit_req`, HAProxy `stick-table`, etc.) and treat the in-process caps as a defense-in-depth backstop.
- `RATE_LIMIT_CLIENT_IP_HEADER` — name of a single-value header the reverse proxy injects with the real client IP (e.g. `X-Real-IP`). When set and the request's TCP peer is loopback or in `RATE_LIMIT_TRUSTED_PROXY_IPS`, the rate limiter and audit-log `remote=` field both key on the trusted-header value instead of the proxy's peer address, so a single grep for one client IP correlates rate-limit rejections AND the auth events that triggered them. The header value must be ONE IP literal -- comma-separated chains (the natural form of `X-Forwarded-For` for multi-hop proxies, e.g. `1.2.3.4, 5.6.7.8`) are deliberately ignored, and the server falls back to the TCP peer; configure the proxy to extract the left-most untrusted hop and re-emit it as a single-value header (most proxies expose `X-Real-IP` or equivalent for exactly this), or place the rate limiter knob behind a proxy that already does the unwrap. Do NOT set this if the app is directly internet-facing -- clients can spoof the header.
- `RATE_LIMIT_TRUSTED_PROXY_IPS` — comma-separated allowlist of proxy peer IP literals authorized to inject `RATE_LIMIT_CLIENT_IP_HEADER`. Same-host loopback proxies are trusted automatically; this knob is for proxies on a different host. The IP comparison is exact (no CIDR support); list each proxy explicitly. **IPv4 and IPv6 are both accepted in any canonicalizable form** -- the parser at `RateLimit.scala`'s `parseTrustedClientIpLiteral` runs each entry through `InetAddress.getByName(value).getHostAddress()` at startup AND runs the runtime peer's `address.getHostAddress()` through the same canonicalization, so `RATE_LIMIT_TRUSTED_PROXY_IPS=::1` matches a peer connecting from `0:0:0:0:0:0:0:1` and vice versa, regardless of compression-or-not. **Do NOT bracket IPv6** literals -- `[::1]` is rejected at startup with `--rateLimitTrustedProxyIps must contain comma-separated IP literals; invalid entry: [::1]` because the parser only accepts the bare form (consistent with how `RATE_LIMIT_CLIENT_IP_HEADER` values arrive from a proxy header, which inject the unbracketed IP). Whitespace around comma separators is trimmed, so `RATE_LIMIT_TRUSTED_PROXY_IPS="10.0.0.1, 10.0.0.2 , ::1"` is equivalent to the compact `"10.0.0.1,10.0.0.2,::1"`. Empty entries between commas (`"10.0.0.1,,10.0.0.2"`) are silently dropped, not treated as errors. Any entry that fails the parse stops startup -- the server fails fast rather than silently ignoring a typo'd allowlist entry that would have been the operator's intended-but-invalid trust target.
- The active client-IP policy that emerges from `RATE_LIMIT_CLIENT_IP_HEADER` + `RATE_LIMIT_TRUSTED_PROXY_IPS` is surfaced in `/api/health` as `rateLimitClientIpSource` (and in the startup-banner log line as `rateLimitClientIpSource=...`, `%20`-escaped) with one of three exact string values: `remote-address` (no header configured -- rate limiting + audit `remote=` both key on the direct TCP peer), `header:<headerName> via loopback-only` (header set but `RATE_LIMIT_TRUSTED_PROXY_IPS` is empty, so only loopback peers can inject it), or `header:<headerName> via loopback-or-allowlisted-proxy` (header set AND non-empty `RATE_LIMIT_TRUSTED_PROXY_IPS`, so loopback OR any allowlisted proxy IP can inject it). A dashboard switching on this field can therefore tell the three policies apart by exact string match without re-parsing the underlying knobs.

Set any of the three caps to `0` to disable that bucket. Only trust a client IP header when the app is behind a proxy you control.

## Reverse Proxy And Exposure

- Keep the raw app on loopback unless you intentionally want LAN exposure
- If you intentionally bind to `0.0.0.0`, a LAN IP, or another non-loopback host without auth, set `ALLOW_UNAUTHENTICATED_PUBLIC_BIND=true` in `conf/hand-history-web.env` so that choice is explicit
- Put HTTPS and stronger edge rate limiting in front of the app for internet-facing deployments
- Use `/api/ready` for load balancers and service managers
- Use `/api/health` for liveness and coarse metrics
- Configure the proxy to **preserve, not strip**, the response headers the origin emits:
  - `Content-Encoding: gzip` + `Vary: Accept-Encoding` — the origin negotiates gzip itself; stripping `Vary` would cause the proxy to serve gzipped bodies to clients that don't accept gzip
  - `ETag` + `Last-Modified` — preserve so the proxy and client can revalidate; the origin honors `If-None-Match` and `If-Modified-Since` and replies `304` to save bandwidth. The origin emits **weak** ETags only (`W/"size-mtime"` for the verbatim static body, `W/"size-mtime-gz"` for the gzipped variant -- the `-gz` suffix gives each encoding a distinct opaque-tag so caches that key only on ETag still distinguish encodings even when an upstream proxy strips `Vary: Accept-Encoding`), and the `If-None-Match` comparison applies RFC 7232 sec 2.3.2 **weak-comparison** semantics: the optional `W/` weak-validator prefix is stripped from BOTH the client value and the server's current ETag before the opaque-tag character-by-character match runs. The defense-in-depth value is the proxy-rewrite-tolerance case: a CDN that strips `W/` in transit (some intermediaries do this when they re-emit ETags through their own validation layer) hands the browser a bare-opaque-tag form `"size-mtime"` to echo back as `If-None-Match`, and the weak-comparison rule still matches that against the origin's `W/"size-mtime"`. Without the prefix-tolerance the revalidation silently fails and the client re-fetches the full body on every poll -- operator-visible only as inflated egress traffic, not as a logged error
  - `Cache-Control` — `no-store` on API responses (do not cache), path-aware `public, max-age=...` on static assets: `vendor/*` gets `public, max-age=31536000` (one year -- vendored libs are pinned by per-filename versioning so the bytes are immutable for the lifetime of the file), all other static paths get `public, max-age=0, must-revalidate` (so a deploy that ships a new `index.html` / `site.js` / `site.css` reaches the user on the next visit without waiting for a TTL to expire). A caching proxy should honor both: long-lived for `vendor/*`, revalidate-each-time for the rest
  - `Content-Security-Policy`, `Permissions-Policy`, `X-Frame-Options`, `Referrer-Policy`, `X-Content-Type-Options`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, `X-Robots-Tag` — defense-in-depth headers the origin sets on every response. A proxy that drops them weakens the browser-side protections; in particular `X-Robots-Tag: noindex, nofollow` prevents search engines from indexing the app if the deployment is accidentally reachable from the public internet.
  - The full `Content-Security-Policy` value the origin emits on every response is: `default-src 'self'; base-uri 'none'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; frame-src 'none'; img-src 'self' data:; manifest-src 'none'; media-src 'none'; object-src 'none'; script-src 'self'; style-src 'self'; worker-src 'none'`. Same-origin (`'self'`) is the only allowed source for the six "where content can load from" directives (`default-src` / `connect-src` / `script-src` / `style-src` / `img-src` / `form-action`); `img-src` ALSO permits `data:` URLs (the only data-URL site needs in shipped markup is the empty inline favicon `<link rel="icon" href="data:,">` in index.html, but the directive permits any `data:` image scheme, not just that exact URL -- which is fine because data-URL images can't execute JavaScript and the other directives still block `data:` for scripts/styles/connects). The remaining seven (`base-uri` / `frame-ancestors` / `frame-src` / `manifest-src` / `media-src` / `object-src` / `worker-src`) are `'none'` so a future injected `<base>`, `<iframe>`, `<object>`/`<embed>`, `<audio>`/`<video>`, `<link rel=manifest>`, or `new Worker(...)` cannot promote itself into a navigation override, framing channel, plugin embed, exfiltration channel, PWA install, or service-worker spawn. A reverse proxy that rewrites the header (some hosting platforms inject their own CSP) MUST keep both the same-origin pins and the explicit `'none'` denials -- relaxing any of them widens the post-compromise blast radius proportional to that directive's reach. The X-Frame-Options: DENY header is paired with `frame-ancestors 'none'` as defense in depth for older browsers that ignore CSP framing rules.
  - The full `Permissions-Policy` value the origin emits on every response denies 36 browser features the app does not use, each with the empty-allowlist syntax `<feature>=()` (no origin -- not even `'self'` -- may invoke the feature). Grouped by category: **hardware / sensors** (`accelerometer`, `ambient-light-sensor`, `battery`, `bluetooth`, `camera`, `display-capture`, `geolocation`, `gyroscope`, `hid`, `idle-detection`, `local-fonts`, `magnetometer`, `microphone`, `midi`, `otp-credentials`, `screen-wake-lock`, `serial`, `usb`, `xr-spatial-tracking` -- 19 features); **media** (`autoplay`, `encrypted-media`, `fullscreen`, `picture-in-picture`, `web-share` -- 5); **identity / payment** (`payment`, `publickey-credentials-get` -- 2); **navigation / document** (`document-domain` -- 1 -- prevents `document.domain=` cross-subdomain origin relaxation); **Privacy-Sandbox + cross-site tracking** (`attribution-reporting`, `browsing-topics`, `interest-cohort` -- the legacy FLoC opt-out kept for older browser builds that haven't migrated to `browsing-topics`, `private-state-token-issuance`, `private-state-token-redemption`, `run-ad-auction`, `shared-storage`, `shared-storage-select-url`, `storage-access` -- 9 features in the Chrome Privacy Sandbox surface that a private poker review tool has no business participating in -- 19+5+2+1+9 = 36 total). Same defense-in-depth rationale as CSP's `'none'` directives: a future XSS or compromised vendored library cannot promote itself into the user's hardware (camera / microphone / USB / serial), browser-level capabilities (geolocation / payment / WebAuthn), or cross-site ad-measurement APIs. A reverse proxy that rewrites `Permissions-Policy` (some hosting platforms inject their own; some app-platform tiers strip user-set headers in favor of a platform default) MUST preserve the full deny-list -- relaxing any directive widens the post-compromise blast radius proportional to that capability's reach, and the hardware + payment + cross-site-tracking subgroups in particular are the highest-impact to keep empty.
  - The remaining single-value security headers each carry a fixed setting: `Referrer-Policy: no-referrer` (strictest possible value -- no `Referer` is ever sent on outbound navigations or fetches, so the user's path through this app doesn't leak to any third-party origin the user later visits via a link or redirect; one tier stricter than the browser-default `strict-origin-when-cross-origin`, which would still leak the origin in some cross-site cases); `X-Content-Type-Options: nosniff` (forces the browser to honor the declared `Content-Type` rather than MIME-sniffing the body, closing the JS-execution-via-uploaded-image / scripted-PDF attack family); `X-Frame-Options: DENY` (no framing at all -- paired with CSP `frame-ancestors 'none'` as defense in depth for older browsers that don't honor CSP framing rules); `Cross-Origin-Opener-Policy: same-origin` (isolates the page from cross-origin opener references, closing XS-Leaks / Spectre process-isolation attack surface -- a cross-origin opener with a `window.opener` reference back to this page is severed at navigation time); `Cross-Origin-Resource-Policy: same-origin` (blocks this app's resources from being embedded by cross-origin documents -- the inverse of COOP, covers `<script src=this-app/...>` / `<img src=this-app/...>` etc. from outside origins, additive on top of CORS); and `X-Robots-Tag: noindex, nofollow` (search engines that honor the header must not index the response nor follow URLs it references; complements the `<meta name="robots" content="noindex, nofollow">` in `index.html`). All six are fixed and not operator-tunable; a reverse proxy that rewrites any of them MUST preserve the strict values, and platforms that strip user-set headers in favor of a default need a per-app override (the platform default is typically weaker than this set).
- The origin emits no CORS response headers (`Access-Control-Allow-Origin`, `-Methods`, `-Headers`, `-Credentials`); OPTIONS preflight responses carry only the `Allow:` method-discovery header per RFC 7231 sec 4.3.7. A different-origin browser XHR / fetch is therefore blocked by the same-origin policy -- the missing `Access-Control-Allow-Origin` fails the preflight gate regardless of cookies or auth. The CSP `connect-src 'self'` directive above layers defense in depth from the inside: it also blocks the same-origin frontend from issuing cross-origin fetches, so an injected script cannot smuggle data out to an attacker-controlled origin even if it gets executed. Operators who need a different-origin client (e.g., a dashboard or programmatic consumer hosted elsewhere) to talk to this API must front the service with a reverse proxy that injects the right CORS headers -- or co-locate the client on the same origin. The in-process server intentionally has no CORS knob to turn on.
- The origin does NOT emit `Strict-Transport-Security` because it does not terminate TLS. For internet-facing deployments behind an HTTPS-terminating proxy, configure the proxy to add an HSTS header (e.g. `Strict-Transport-Security: max-age=31536000; includeSubDomains`). Recommended only AFTER the deployment is verified to work over HTTPS — once `max-age` is in flight a browser refuses to fall back to HTTP for that host, so a misconfigured HSTS during testing can lock you out of plain-HTTP access until the header's TTL expires. For private-network/loopback deployments, HSTS is unnecessary.

## Logs And Observability

- The service helper scripts route stdout/stderr to files under `logs/`. Tail those or pipe to a log aggregator.
- `/api/health` always returns `200` while the process is up -- there is NO `503` path on this endpoint (readiness gating lives on `/api/ready` only; `/api/health` is a pure liveness probe and does not gate on draining, queue saturation, or timed-out-worker state). The JSON body opens with a hardcoded `ok: true` invariant (literal `Bool(true)` at `Readiness.scala`'s `renderHealth`; never `false` -- if the JVM were too sick to set the field the request would never return at all), so a monitor can key on `body.ok === true` as the always-up signal separately from the rich-state fields below, and a dashboard alert on `ok != true` triggers only on actual transport failure (TCP refused / DNS / HTTP-layer error) rather than on application-level state. It reports configuration + queue state (auth mode, rate-limit caps, max concurrent/queued jobs, `analysisTimeoutMs`, `playingHallTimeoutMs`, `maxUploadBytes`, active HTTP requests, queued/running jobs, timed-out workers still unwinding, retained terminal jobs, the machine-readable readiness reason as `readyReason` -- same enum as `/api/ready`'s `reason` field (`accepting-traffic` / `draining` / `timed-out-worker` / `queue-full`) but surfaced under a different field name on each endpoint, so a dashboard parsing both probes reads `readyReason` here and `reason` there, plus `service`/`host`/`port`/`startedAtEpochMs`/`uptimeMs` for fleet correlation). Under platform-user auth it also reports user-store metrics: `userAuthMaxUsers` (the cap), `userAuthStoredUsers` (current count -- dashboard at e.g. 80%/90% to spot capacity pressure before legitimate registrations fail), `userAuthActiveSessions` (live in-memory session count -- an off-hours spike is a credential-stuffing-success / leaked-automation heads-up), and `userAuthPendingOidcFlows` (started but not callback-completed OIDC flows -- a /start storm with no completions usually means a misconfigured provider redirect URI). All four are `null` in basic-auth and no-auth modes. Use it for dashboards.
- `/api/ready` is the readiness endpoint for reverse proxies / service managers (same verb set as `/api/health`: `GET`, `HEAD`, `OPTIONS`). It returns `200` only when the instance is accepting new analysis work and switches to `503` when the queue is saturated, the instance is draining, or a timed-out worker is still unwinding. The response also reports `ready` + `reason` (machine-readable: same enum as `/api/health`'s `readyReason` -- `accepting-traffic` / `draining` / `timed-out-worker` / `queue-full` -- under the field name `reason` on this endpoint), `draining` + `acceptingAnalysisJobs` + `drainSignalConfigured` + `drainSignalPresent` (so a probe can tell "queue full" from "operator-initiated drain" without a separate health check), the configured `analysisTimeoutMs` / `playingHallTimeoutMs` / `timedOutWorkersInFlight` / `activeHttpRequests` / `maxConcurrentJobs` / `maxQueuedJobs` / `queuedJobs` / `runningJobs` (so a load balancer can plot saturation alongside the bare ready/not-ready bit), auth mode, the submit/status/auth rate-limit settings, the `rateLimitClientIpSource` policy string (same field + same three exact string values as `/api/health` -- enumerated above), and `service`/`host`/`port` for fleet correlation. Use it for load-balancer health checks; the field set is a strict subset of `/api/health`'s plus the renamed `reason` -- a probe wired against either endpoint can pick which level of detail it needs.
- Auth events emit structured log lines: `auth.login.success`, `auth.login.failure`, `auth.register.success`, `auth.register.failure`, `auth.logout`, `auth.oidc.start`, `auth.oidc.start.failure`, `auth.oidc.success`, `auth.oidc.failure`. INFO level for success/expected events, WARN for failures. Each line carries `remote=` (on every auth.* event) plus -- on the local-auth events (`auth.login.{success,failure}`, `auth.register.{success,failure}`, `auth.logout`) and the post-callback `auth.oidc.success` -- an `email=` field. The OIDC `auth.oidc.start` / `auth.oidc.start.failure` / `auth.oidc.failure` lines do NOT carry `email=` because the OIDC flow doesn't yield a user email until the userinfo response completes -- `start` and `start.failure` fire before the provider redirect, and the callback `failure` paths exit before (or because of) the userinfo step that would have resolved one. They instead carry `provider=<id>` so the operator can tell Google-flow failures from a future multi-provider deployment's other-IdP failures. A high WARN rate from a single `remote=` reveals brute-force or credential-stuffing attempts; a high WARN rate from a known `email=` from many `remote=` sources may be a single-account-targeted credential-stuffing probe. Success lines log the **canonical** (normalized: zero-width-character strip → trim → lowercase, all under `Locale.ROOT`) email so all events for one user grep identically; failure lines log the **submitted** email so brute-force probes are visible in the form the attacker typed. The zero-width-strip step (the first stage of `PlatformUserAuth.normalizeEmail`) removes the BOM (U+FEFF) and the U+200B/200C/200D/2060 family BEFORE the trim+lowercase pair, because `String.trim` only removes chars ≤ 0x20 and `Character.isWhitespace` also rejects those zero-width codepoints -- without the strip, a user pasting their email from a UTF-8-with-BOM editor or a clipboard pipeline that injects zero-width chars would register with an invisible byte embedded in the canonical record AND then never be able to log in (their later typed input lacks the invisible byte; the stored-vs-submitted comparison misses; the same timing-uniform `"invalid email or password"` Left value blocks the failure mode from being operator-visible).
- `remote=` is the **resolved client identity**, not necessarily the TCP peer. When `RATE_LIMIT_CLIENT_IP_HEADER` is set and the peer is loopback or in `RATE_LIMIT_TRUSTED_PROXY_IPS`, `remote=` is the IP the trusted header resolves to (no port — `X-Forwarded-For`/`X-Real-IP` carry none). Otherwise it's the direct TCP peer as `host:port` with IPv6 bracketed per RFC 3986 §3.2.2. This matches the rate-limit `clientKey=` field so an operator grepping for one IP sees both rate-limit rejections AND the auth events that triggered them.
- The OIDC `/start` endpoint Set-Cookies a short-lived (10-minute, `HttpOnly`, `SameSite=Lax`) state cookie -- `sicfun_oidc_state` in insecure mode, `__Host-sicfun_oidc_state` when `USER_AUTH_COOKIE_SECURE=true` (same `__Host-` prefix and same operator-side log-grep / proxy-ACL consideration as the session cookie, plus `Secure` in secure mode) -- bound to the random state value embedded in the provider redirect URL. The `/callback` endpoint requires the cookie to match the URL `state` parameter before exchanging the authorization code — an OAuth 2.0 BCP "covert-redirect" / login-CSRF mitigation. If the cookie is missing or mismatched, the callback redirects to the failure landing page with `?auth_error=missing_state_cookie` or `?auth_error=state_cookie_mismatch` rather than calling the provider's token endpoint. The redirect URI also sets `prompt=select_account` on Google's authorization endpoint, so every `/start` forces Google's account picker even when the user has exactly one Google account already signed in — useful for multi-account users (Work vs personal Google), and an explainer for the "why does it ask me every time?" support question on single-account users.
- `auth.oidc.failure` lines carry a `reason=` value naming the failure category. Five distinct patterns, from earliest fire-stage to latest: `missing_state_cookie` / `state_cookie_mismatch` (state-binding check failed, see the bullet above); `provider-error:<oauth_error_code>` when the provider sent a `?error=<code>` callback before we got to talk to it (`provider-error:access_denied` is a user-declined sign-in, `provider-error:temporarily_unavailable` is a provider outage, `provider-error:invalid_request` and others are RFC 6749 §5.2 standard codes); `oversize_callback_param` when either the `state` or `code` query param exceeds 256 chars (an attacker probing the callback shape rather than legitimate provider traffic); `missing_code_or_state` when one of the two required query params is absent (truncated redirect, browser-side history-modification, etc.); and a variable-content reason for failures downstream of the state check, drawn from this fixed set of 13 finishOidc Left values (all space-bearing, so they grep as `%20`-escaped in the actual log line). **From the OIDC state-store consume step (1 string):** `OIDC login state expired or is invalid` (state-store TTL expired between `/start` and `/callback`, or the state cookie matched a value our store never issued / already consumed). **From the Google token + userinfo HTTP exchange (3 strings):** `Google token exchange failed with status <N>` (token endpoint returned non-2xx -- includes PKCE verifier mismatch which Google surfaces as a 400); `Google token exchange did not return an access token` (token endpoint returned 2xx but the `access_token` field was missing -- a pathological-provider / upstream-tampering signal); `Google userinfo request failed with status <N>` (userinfo endpoint returned non-2xx after a successful token exchange). **From parsing the userinfo response body (2 strings):** `Google did not return a verified email address for this account` (userinfo came back 2xx but `email_verified: false`, so we refuse to bind the identity); `Google userinfo response was missing required identity fields` (userinfo came back 2xx but `sub` / `email` / `name` were all empty after trimming -- a malformed-provider or scope-misconfiguration signal). **From re-validating the OIDC-provided email through the same `validateEmail` the local-register path uses (3 strings):** `email must be at most 254 characters`; `email must not contain whitespace or control characters`; `email must be a valid address` (the provider would have to deliver an extremely malformed value to trip these in practice, but defense-in-depth applies the same validation upstream). **From `upsertOidcIdentity` integrity checks (1 string):** `OIDC subject is too long` (the provider-supplied `sub` claim exceeded 256 chars, bounded so a hostile provider can't poison the user store with megabyte-sized subjects that double as map keys). **From the user-record write paths (2 strings):** `an account with that email already exists; sign in with its existing method` (the OIDC-vs-local collision documented in the user-store section above -- the Google email matched an existing local-password account); `registration is temporarily unavailable` (OIDC sign-up tripped the same `USER_AUTH_MAX_USERS` cap that bounds local registration, so the deployment refuses new OIDC accounts too). **And the catch-all (1 string):** `Google OIDC exchange failed: <upstream-message>` (NonFatal exception thrown mid-exchange: network failure, the connect/request timeouts named in the Optional OIDC section, JSON parse error on a malformed provider response, etc.). The bundled frontend (`site.js`'s `lookupOidcErrorMessage` -- exact-match table at `OIDC_ERROR_MESSAGES` with prefix-pattern fallbacks for the three Google-exchange strings that embed a variable suffix) maps each of the 13 finishOidc Left values to a user-facing message and clears the `?auth_error=` query string on render so the failure landing URL stays clean across refreshes. Line references intentionally omitted -- the doc previously cited an "at line 1328" anchor that was 257 lines stale by the time of this update; the symbol names above are stable enough to grep for and don't rot when the file grows.
- Job lifecycle events log to stderr at INFO/WARN with specific prefixes a log-monitoring rule can match on: `job accepted`, `job started`, `job completed` (all INFO), `job rejected unavailable`, `job rejected queue full`, `job failed`, `job timed out` (all WARN). Playing Hall jobs emit a parallel set under the prefix `playing hall job ...`, plus `playing hall job cancelled` (INFO) when the DELETE-cancel path interrupts a running worker. Each line carries `jobId=` (omitted on the rejection-prefix lines `... rejected unavailable` and `... queue full`, which represent admission failures and don't surface a jobId in the log) plus a context-appropriate subset of `queuedJobs=` / `runningJobs=` / `durationMs=` / `errorStatus=` / `timeoutMs=` / `error=` / `reason=`; the `... queue full` lines additionally carry `maxConcurrentJobs=` and `maxQueuedJobs=` so an operator chasing a capacity-cap rejection can confirm which cap fired straight from the log line without re-reading the running config. Enough to chart submit→start latency, completion-rate, timeout-rate, and queue depth from the audit log alone.
- Rate-limit rejections log as `request rate limited path=... client=... bucket=... limitPerMinute=... retryAfterMs=...` at WARN. `client=` is `user:<userId>` when a platform-user session is on the request, `header:<ip>` when `RATE_LIMIT_CLIENT_IP_HEADER` is configured and the TCP peer is in the trusted set, or `remote:<addr>` (TCP peer) otherwise — the user-keyed form means a noisy authenticated user does not throttle unrelated users behind the same NAT. `bucket=` is one of `submit` / `job-status` / `auth`.
- Unauthenticated requests against protected paths log as `request unauthorized path=... remote=... reason=...` at WARN. The `reason=` value names the specific auth-stage failure -- under Basic auth: `missing_authorization` (no `Authorization:` header), `unsupported_authorization_scheme` (header present but not `Basic`), `malformed_authorization` (Basic but the base64 payload doesn't decode to `user:password`), or `invalid_credentials` (decoded fine but the username/password compare failed; constant-time `&` compare means a credential-stuffing probe can't time-distinguish wrong-username from right-username-wrong-password). Under platform-user auth: `session-missing-or-invalid`, which has two distinct underlying subcases worth distinguishing (the log line collapses both into the same `reason=` value, so an operator triaging the pattern needs to know what to correlate against): **no cookie on the request** -- most commonly because the session cookie's `Max-Age` expired client-side at exactly `loginTime + USER_AUTH_SESSION_TTL_MS` (default 12h, FIXED from login time regardless of activity -- see the `USER_AUTH_SESSION_TTL_MS` bullet above for the record-slides-but-cookie-doesn't mechanic), or because the user cleared cookies / closed a private-browsing window; **cookie present but doesn't resolve** -- the server-side record expired (idle user past ttlMs without any auth request), got revoked by an explicit logout in a sibling tab (correlate against the user's `auth.logout` log line), or was dropped by a server restart (correlate against the most recent `shutdown requested` log line). Five distinct strings total; an alert rule filtering on `reason=invalid_credentials` plus a high WARN rate from one `remote=` is the credential-stuffing-against-Basic signal, and the same shape with `reason=session-missing-or-invalid` for platform-user is the cookie-replay / leaked-session probe.
- CSRF-failed state-changing requests (POST/DELETE on auth/logout, auth/profile, analyze-hand-history, playing-hall) log as `request forbidden path=... remote=... email=... reason=csrf-missing-or-invalid` at WARN. A burst from one `remote=` against many endpoints is a likely automated probe; the same from a known user usually means their JS frontend lost the cookie mid-session.
- NSSM rotates the service stdout/stderr logs at 10 MB (`AppRotateBytes=10485760`, `AppRotateOnline=1`). Rotated files keep their timestamp suffix in `logs/`; nothing deletes them automatically, so prune or ship them off the host periodically if the audit history matters and the partition is small.
- Structured-log values that could legitimately contain a space — submitted email at register/login, analyze `heroName=`, startup banner `modelSource=` / `drainSignalFile=` / `rateLimitClientIpSource=`, plus the `reason=` field in admission-rejected log lines (both `job rejected unavailable` for analyze and the parallel `playing hall job rejected unavailable` for Playing Hall) and auth-failure (`auth.register.failure`, `auth.login.failure`, `auth.oidc.start.failure`, `auth.oidc.failure`) log lines, and the `error=` field in failed-job log lines (both `job failed` for analyze and the parallel `playing hall job failed` for Playing Hall) — are `%20`-escaped before they reach the log line. Without this, a Windows path like `C:\Program Files\model`, a hero name like `"Alice Smith"`, or a backend message like `analysis timed out after 120000ms` would split the surrounding key=value pairs and confuse log aggregators that tokenize on whitespace. Operator-facing: when you grep for an email, path, or other space-bearing value in the logs, type the value with `%20` in place of any space.

## State And Backups

- In-flight and completed review jobs are in-memory only
- A restart drops queued/running jobs
- In-flight OIDC sign-in state is also in-memory only -- the `OidcStateStore` holds the random `state` token issued by `/start` until `/callback` consumes it, and a restart drops the store. Any user who clicked Continue with Google but hasn't yet completed the callback round-trip sees `?auth_error=OIDC login state expired or is invalid` (translated by the bundled UI to "Your sign-in took too long...") when they land back at `/callback`. The state cookie's 10-minute TTL already loses an idle flow at that mark regardless; restarts collapse the window for currently-active flows. Operationally minor (the affected user clicks Continue with Google again), but `/api/health.userAuthPendingOidcFlows` reflects the in-memory count -- if a non-trivial number is visible right before a planned restart, you might delay it or warn the user base.
- Active platform-user sessions are ALSO in-memory only -- the `SessionManager` holds every signed-in user's session-token + last-seen timestamp + CSRF token until the session is explicitly revoked (logout / re-auth via OIDC) or ages off its sliding `USER_AUTH_SESSION_TTL_MS` window (default 12h). A restart drops the store, so every currently-signed-in user's next request 401s with `reason=session-missing-or-invalid` and the bundled frontend re-prompts them to sign in. The browser still holds the session cookie (cookies are client-side state, not invalidated by the server going down), but its token no longer resolves to any record server-side and falls through to the same not-signed-in path as a never-existed cookie. Operationally: a planned restart logs out all currently-active users; signed-in counts in dashboards drop to zero at the restart and rebuild as users re-sign-in. `/api/health.userAuthActiveSessions` reflects the in-memory count -- useful for sizing the post-restart re-auth burst on a busy deployment (every active session will hit `/api/auth/login` within seconds-to-minutes once users notice their state was lost, so the `RATE_LIMIT_AUTH_PER_MINUTE` cap may briefly throttle the legitimate post-restart re-auth wave if `userAuthActiveSessions` was high pre-restart). Persistent account data (password hashes, profile fields, linked-provider identities) under `USER_STORE_PATH` survives the restart unchanged -- only the EPHEMERAL session state is lost, not the user accounts.
- Platform-user auth persists account/profile data under `USER_STORE_PATH`. The file contains email addresses, PBKDF2-HMAC-SHA256 password hashes (per-account salted with 128-bit random salt, 210,000 iterations, 256-bit output -- meets NIST SP 800-132 §5.1 floor of ≥128-bit salt and ≥256-bit output; not plaintext), profile fields (displayName, heroName, preferredSite, timeZone), OIDC subject identifiers, per-account UUIDs (internal `userId`), and event timestamps (`createdAtEpochMs` / `updatedAtEpochMs` / `lastLoginAtEpochMs`). Treat it as PII: restrict filesystem permissions to the service account (e.g. `icacls` on Windows or `chmod 600` + correct owner on Linux), encrypt backups, and keep it off any tier where unprivileged readers could grep it. A leaked store is not a credential leak (the hashes resist offline cracking), but the linked emails + OIDC subjects + profile fields are still PII a compliance audit would flag.
- Back up `conf/hand-history-web.env` and `USER_STORE_PATH` if they matter operationally. `hand-history-web.env` contains the Basic-auth credentials and/or `GOOGLE_OIDC_CLIENT_SECRET` in plaintext if either is configured; back up with the same protections you give other secrets.

## Bundle Integrity

Verify the shipped bundle after copy/deploy:

```powershell
powershell -ExecutionPolicy Bypass -File .\bin\verify-release-manifest.ps1
```

That script checks every shipped file against `manifest.sha256` and fails if a file is missing, added, or modified. Runtime marker files at the bundle root (filenames starting with `.`, e.g. `.manifest-verified` written by the installer-variant's `Setup.cmd`) are intentionally ignored.

The installer variant's `Setup.cmd` calls `bin\verify-if-needed.ps1` instead of running the full verifier on every launch. That helper writes a `.manifest-verified` marker after a successful check and short-circuits subsequent launches as long as the marker's timestamp is at least as new as `manifest.sha256`. Re-extracting the bundle advances `manifest.sha256`'s mtime and triggers a fresh verification. To force a re-verify manually, delete `.manifest-verified` at the bundle root.
